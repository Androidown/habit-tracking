# 可用性测试方案

## 1. 概述

### 1.1 测试目标

本次可用性测试旨在验证个人习惯打卡管理工具的核心操作路径是否达到 PRD（[DEM-139](mention://issue/关联的PRD)）定义的成功指标，发现可用性问题并为上线前改进提供依据。

**核心验证指标**：

| 指标 | 目标值 | 来源 |
|------|-------|------|
| 首次创建习惯并完成一次打卡 | ≤ 60 秒（中位数） | PRD 成功指标 |
| 核心操作路径步数 | ≤ 3 步 | PRD 成功指标 |
| 今日待办可见率 | 100% | PRD 成功指标 |
| 连续天数展示覆盖率 | ≥ 90% | PRD 成功指标 |
| 任务完成率 | ≥ 80%（每项任务） | 团队内部目标 |

### 1.2 测试方法

- **方法**：一对一 Moderated 可用性测试，远程（视频会议共享屏幕）或线下面对面
- **形式**：参与者按预设任务脚本操作产品原型/预发布版本，同时「出声思考」
- **数据采集**：任务完成时间、操作路径步数、完成/失败记录、关键问题观察、事后简短访谈
- **预计时长**：每位参与者 30-45 分钟

## 2. 参与者招募

### 2.1 招募条件

筛选条件详见《参与者筛选问卷》（[participant-screener.md](./participant-screener.md)）。

**概要**：
- **人数**：≥ 5 名有效参与者（建议招募 6-8 名以应对缺席）
- **年龄**：18-50 岁
- **核心条件**：日常使用手机（日均 ≥ 1 小时）、有习惯养成类需求或使用过同类 App
- **排除**：互联网产品/交互设计从业者、近 3 个月内参加过可用性测试者、团队内部成员

### 2.2 目标用户画像（PRD DEM-139）

| 画像 | 描述 | 在测试中的代表 |
|------|------|--------------|
| **忙碌上班族**（核心） | 25-40 岁白领/职员，工作繁忙，希望通过零碎时间管理习惯 | 至少 2-3 名 |
| **自律提升者** | 20-35 岁学生/初入职场，有明确自我提升目标，关注连续天数和统计 | 至少 1-2 名 |
| **轻量用户** | 30-50 岁，对 App 操作不熟悉，需要极简引导 | 至少 1 名 |

### 2.3 参与配额

| 维度 | 配额 |
|------|------|
| 年龄覆盖 | 至少 2 个年龄段 |
| 习惯 App 经验 | 至少 1 名新手 + 1 名有经验用户 |
| 合计人数 | ≥ 5 人 |

## 3. 测试任务脚本

### 3.1 任务一：创建习惯

| 项目 | 内容 |
|------|------|
| **编号** | T1 |
| **测试项** | 创建个人习惯 |
| **对应验收** | 验收标准第 2 条：「设计并执行可用性测试任务：创建习惯、每日打卡、查看打卡统计」 |
| **PRD 指标关联** | 操作路径 ≤ 3 步；首次打卡 ≤ 60 秒（与本任务及 T2 连贯计时） |

**起始指令（读给参与者）**：

> 「假设您最近想养成一个『每天阅读 30 分钟』的习惯。请打开这个工具，创建一个名为『每日阅读』的新习惯，执行周期设置为『每天』。」

**预期操作路径**：
1. 打开首页 → 找到「创建习惯」入口
2. 填写习惯名称及执行周期
3. 点击「保存/创建」确认

**成功判断标准**：
- □ 成功创建习惯「每日阅读」，显示在习惯列表中
- □ 创建过程无错误提示

**操作耗时上限**：≤ 60 秒（从打开首页到创建成功）
**操作路径步数上限**：≤ 5 步（含点击、输入、确认等操作，不含文字输入中的按键）

**主持人观察要点**：
- 能否在 5 秒内找到「创建习惯」入口
- 填写习惯名称时是否有困惑
- 执行周期设置（「每天」）是否容易理解和操作
- 创建成功后是否有明确反馈

---

### 3.2 任务二：每日打卡

| 项目 | 内容 |
|------|------|
| **编号** | T2 |
| **测试项** | 对已创建的习惯完成今日打卡 |
| **对应验收** | 验收标准第 2 条 |
| **PRD 指标关联** | 操作路径 ≤ 3 步；首次打卡 ≤ 60 秒（与 T1 连贯计时）；今日待办可见率 100% |

**前置条件**：任务一已完成（习惯「每日阅读」已存在）

**起始指令（读给参与者）**：

> 「假设现在是第二天，您想标记已完成今天的『每日阅读』。请找到今天的待办并打卡。」

**预期操作路径**：
1. 打开首页 → 看到「今日待办」列表
2. 找到「每日阅读」习惯
3. 点击打卡按钮完成

**成功判断标准**：
- □ 成功打卡「每日阅读」今日完成
- □ 打卡后状态反馈清晰（如按钮变为已完成/对勾）
- □ 「今日待办」清单中「每日阅读」出现在列表中（可见率）

**操作耗时上限**：≤ 30 秒（从打开首页到打卡成功）
**操作路径步数上限**：≤ 3 步

**主持人观察要点**：
- 「今日待办」是否在首屏明显位置
- 打卡按钮是否易于点击（触控区域 ≥ 44×44px）
- 打卡后是否有视觉反馈（颜色变化、动画等）
- 是否出现误操作（如点到取消或编辑）

**扩展观察（如时间允许）**：
- 取消打卡操作是否能自然发现
- 连续打卡多天的流程是否顺畅

---

### 3.3 任务三：查看打卡统计

| 项目 | 内容 |
|------|------|
| **编号** | T3 |
| **测试项** | 查看习惯的打卡统计信息 |
| **对应验收** | 验收标准第 2 条 |
| **PRD 指标关联** | 连续天数展示覆盖率 ≥ 90% |

**前置条件**：已在系统中存在至少 1 个习惯且有若干天的打卡记录（可由主持人提前准备或任务一/二累积）

**起始指令（读给参与者）**：

> 「请查看您『每日阅读』习惯的打卡情况，告诉我您一共连续打卡了多少天。」

**预期操作路径**：
1. 打开首页 → 找到目标习惯
2. 点击习惯进入详情页
3. 在详情页中找到连续天数/统计信息

**成功判断标准**：
- □ 能成功找到习惯详情/统计页面
- □ 能正确读出连续打卡天数
- □ 统计信息展示清晰（包含累计完成次数、连续天数等）

**操作耗时上限**：≤ 40 秒
**操作路径步数上限**：≤ 4 步

**主持人观察要点**：
- 能否自然找到习惯的详细统计入口
- 连续天数信息的呈现方式是否一目了然
- 日历视图是否能被用户发现和使用
- 统计数据对用户是否有鼓励/激励效果

**扩展观察（如时间允许）**：
- 切换日历视图（月视图）浏览历史记录
- 查看不同习惯的统计对比

## 4. 执行计划

### 4.1 测试环境

| 项目 | 要求 |
|------|------|
| 测试环境 | 预发布/Staging 环境，或本地运行的最新 develop 构建 |
| 设备 | 参与者自用设备（手机浏览器），推荐手机端优先 |
| 浏览器 | Chrome/Safari/Edge 最新版本 |
| 网络 | 正常家庭/WiFi 网络 |
| 远程工具 | 腾讯会议 / Zoom（含屏幕共享功能） |
| 录制 | 征得同意后录制屏幕+音频 |

### 4.2 测试流程（每位参与者）

| 环节 | 时长 | 说明 |
|------|------|-----|
| 欢迎与介绍 | 5 min | 介绍测试目的、流程，强调「测试产品非测试人」，签署知情同意书 |
| 背景访谈 | 3 min | 快速了解参与者的习惯养成经历、工具使用情况 |
| 任务一：创建习惯（T1） | 5 min | 含任务执行+主持人记录 |
| 任务二：每日打卡（T2） | 5 min | 含任务执行+主持人记录 |
| 任务三：查看统计（T3） | 5 min | 含任务执行+主持人记录 |
| 自由探索 | 5 min | 参与者自由试用产品其他功能，无脚本限制 |
| 简短访谈 | 5 min | 收集整体感受、最满意/最困惑的点、改进建议 |
| 总结致谢 | 2 min | 告知后续安排，赠送感谢礼物（如有） |
| **合计** | **~30 min** | |

## 6. 成功标准汇总

| 维度 | 指标 | 目标值 | 衡量方式 |
|------|------|-------|---------|
| **效率** | 首次创建习惯→打卡完成总时长 | 中位数 ≤ 60 秒 | T1+T2 连贯计时 |
| **效率** | 单次打卡耗时 | 中位数 ≤ 30 秒 | T2 计时 |
| **效率** | 查看统计耗时 | 中位数 ≤ 40 秒 | T3 计时 |
| **效率** | 操作路径步数（打卡） | 中位数 ≤ 3 步 | T2 步数计数 |
| **效率** | 操作路径步数（创建习惯） | 中位数 ≤ 5 步 | T1 步数计数 |
| **完成率** | 各任务独立完成率 | ≥ 80% | 成功完成人数 / 总人数 |
| **满意度** | 整体满意度（1-5 分） | ≥ 4.0 | 事后访谈/问卷 |
| **可见性** | 今日待办可见率 | 100% | T2 中待办项目是否出现在预期位置 |

## 7. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 招募不足 5 人 | 样本量不足，结果缺乏代表性 | 提前启动招募，预留候补名额；降低门槛或扩大渠道 |
| 参与者缺席 | 有效数据减少 | 招募 6-8 名，预留候补；提前一天确认 |
| 测试环境不稳定（网络/服务） | 任务中断，数据无效 | 准备本地运行版本作为备用；预先检查环境 |
| 参与者对技术操作不熟悉 | 数据偏差（测的是操作能力而非产品） | 主持人在任务前做简短演示；测试非产品熟悉度 |
| 录制设备故障 | 无法回看分析 | 主持人同时手写笔记作为备份 |

2. **PRD 成功指标达标评估**：逐项评估指标达成情况
3. **改进计划**：对未达标指标标记具体改进措施、优先级与责任方
4. **原始数据归档**：录制文件、笔记、筛选问卷等
